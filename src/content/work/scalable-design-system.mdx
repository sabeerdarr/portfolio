## Executive summary

An analytics SaaS had grown for four years without a design system. The cost had become
visible: 23 button variants, four grey palettes, and every feature negotiating its UI from
scratch. This project built a design system deliberately sized for a five-engineer team — a
disciplined token layer, a small component set chosen by usage data, and a contribution process
lightweight enough to survive contact with real deadlines.

<Callout variant="insight">
  The defining decision was what to leave out. A design system a small team can't maintain is worse
  than none — it decays into one more inconsistent layer. Scope discipline was the strategy, not a
  compromise.
</Callout>

## Project context

Two product squads shipped weekly from a shared codebase, with me as the company's only
designer. Each squad had drifted toward its own conventions. New features took longer than they
should because basic UI decisions kept being re-made, and the product increasingly looked like
two products stitched together.

## Problem

The audit made the drift concrete: 23 button styles, 31 text styles in production against 9 in
any design file, four grey ramps, and three different modal implementations with different
keyboard behaviour — which made this an accessibility problem, not just an aesthetic one.

> The team didn't have a style problem; it had a decision-reuse problem. Every inconsistency was
> a decision made twice by people who couldn't see each other's work.

## Users and audience

A design system's users are the team. Interviews with all five engineers and both PMs surfaced
the requirements that shaped everything:

- Engineers wanted **fewer decisions, not more rules** — "tell me which component to use and
  give me working code."
- PMs wanted **speed and predictability**; they'd trade visual novelty for it without
  hesitation.
- Everyone feared systems bureaucracy: a process that made small changes slow would be routed
  around and then abandoned.

## Business context

The company was preparing for its next funding stage, with product credibility under scrutiny
by prospects doing security-and-polish evaluations. Inconsistent UI read as immaturity in
enterprise sales demos. The system also had to reduce design bottleneck risk: with one
designer, every screen that needed bespoke design was a queue.

## Constraints

- **No dedicated time budget** — the system had to be built alongside feature work, which
  forced incremental delivery from week one.
- **React + CSS custom properties** stack, no appetite for new dependencies.
- **Two existing visual dialects** in production; the system had to converge them without a
  big-bang rewrite.

## Role and responsibilities

I owned the system end-to-end: audit, token architecture, component design, Figma library
structure, documentation, and the contribution process — pairing closely with one engineer per
squad who acted as system champions on the code side.

## Research

The UI inventory doubled as a usage census: every component-like pattern in the product was
catalogued with its frequency. That data drove scope — the system launched with the twelve
components that covered roughly 80% of interface surface, not the fifty a mature system might
have. Everything else stayed bespoke, intentionally, until usage justified promotion.

## Key findings

- Most drift traced to **missing decisions, not ignored ones** — there was no place where "the
  right grey" was written down.
- The four grey palettes weren't taste differences; they were four eras of the product,
  each copy-pasted forward.
- Engineers already reused code informally — the system needed to formalise existing paths,
  not fight them.

## Problem definition

**Design goal:** any engineer can build a standard screen without asking a designer — and the
result looks like it belongs in the product, passes accessibility checks, and stays consistent
in both themes.

## Design exploration and architecture

The token architecture came before any component visuals: a three-tier structure (primitive →
semantic → component) kept the semantic layer small enough to memorise. Naming was tested with
engineers by quiz — if they couldn't guess what `--color-surface-raised` meant without docs,
the name changed.

## Decisions and trade-offs

- **Twelve components, done fully** — each with all states, keyboard behaviour, and docs —
  rather than forty components at 70%. An incomplete component is a support ticket generator.
- **Semantic tokens only in components.** Primitives are private; this made the later
  dark-theme addition a token-mapping exercise instead of a redesign.
- **Documentation lives in Storybook**, next to the code engineers already used — not in a
  separate site nobody would keep open.
- **No visual redesign.** The system canonised the better of the existing dialects. Rebranding
  at the same time would have doubled the risk for zero systems value.

## Components and documentation

Each component shipped as a triplet: Figma component with matching props, coded component in
Storybook, and a usage page answering the three questions engineers actually asked — _when do I
use this, what are the states, what should I not do with it._ Anti-patterns were documented with
the same care as patterns.

## Testing and adoption

A design system's usability test is adoption. Rollout was migration-by-touch: no rewrite
sprints — any screen an engineer touched for feature work got migrated in the same PR. Adoption
was tracked with a simple lint rule counting legacy-pattern imports, giving the team a visible,
falling number.

## Accessibility considerations

The system became the accessibility enforcement layer: focus management, contrast-checked
token pairs, minimum target sizes, and correct semantics were built into components once, which
fixed the three-modals problem structurally. Every component page documents its keyboard
interaction contract.

## Governance and contribution

The contribution process fits on one documentation page: propose in a shared channel, pair
with the designer on the spec, ship with docs. A monthly 30-minute systems review triages
proposals and retires what isn't earning its maintenance cost. Heavyweight RFC processes were
explicitly rejected — the system's governance had to match the team's size.

## Lessons learned

- **Usage data beats ambition for scoping.** The 12-component launch was mocked as small and
  proved exactly right — nothing shipped unfinished, so trust compounded.
- **Champions matter more than mandates.** The per-squad engineer champions did more for
  adoption than any policy could have.
- **Migration-by-touch works** — but only with a visible metric. The falling lint count turned
  migration into a game the team wanted to win.

## What I'd do next

Add automated visual-regression tests to the component library, promote the two most-requested
bespoke patterns (data table filters, bulk actions) into the system, and formalise the content
guidelines that currently live in review comments.
